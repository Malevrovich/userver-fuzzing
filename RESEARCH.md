# Аналоги и обратная связь для фаззинга userver

Дата обзора: 5 октября 2026 года. Изучены документация и исходники; инструменты на userver не запускались. Возможности существующих решений отделены от предложений для проекта. Основная постановка — в [PROJECT.md](PROJECT.md).

## REST-тестирование и генерация запросов

Здесь «поддерживает C++» может означать разные вещи: отправляет HTTP-запросы C++-сервису, получает покрытие его кода или вызывает C++-функцию внутри процесса. Эти возможности нельзя считать взаимозаменяемыми. Аналогично, покрытие операций OpenAPI и итоговый отчёт о покрытии кода не означают, что покрытие направляет генерацию.

| Инструмент | Что уже умеет | Значение для проекта |
| --- | --- | --- |
| [Schemathesis](https://schemathesis.readthedocs.io/en/stable/guides/hypothesis-strategies/) | Генерация по OpenAPI, Hypothesis/pytest, пользовательские проверки, минимизация входов; отдельный stateful-режим | Наиболее близкий кандидат для первого Python-прототипа. Готовое получение покрытия отдельного C++-процесса не подтверждено |
| [RESTler](https://github.com/microsoft/restler-fuzzer) | Stateful REST-фаззинг: зависимости producer–consumer, последовательности, обратная связь из ответов, дополнительные checkers | Аналог для сценариев с зависимыми ID. Документированное API coverage не равно покрытию ветвей C++ |
| [REST Assured](https://github.com/rest-assured/rest-assured/wiki/Usage) | Java DSL для запросов, assertions и проверки JSON Schema ответа | Ориентир для удобного описания тестов; автоматический coverage-guided поиск в этом руководстве не заявлен |
| [Karate](https://docs.karatelabs.io/) | Сценарии API-тестов, параметризация, assertions, передача данных между шагами | Ориентир для сценарного интерфейса; не готовый движок отбора входов по покрытию C++ |

Все эти инструменты могут обращаться к C++-сервису по HTTP. RESTler и Schemathesis существенно ближе к генерации неизвестных тестов, чем библиотеки написания заранее заданных сценариев.

Для Schemathesis есть конкретный путь проверки совместимости: `schemathesis.openapi.from_dict(...)` принимает документ OpenAPI; `schema[path][method].as_strategy()` даёт Hypothesis-стратегию объекта запроса. Для отдельной JSON Schema тела нужен небольшой OpenAPI-документ вокруг неё. Режим positive соответствует нашему первому этапу. [Python API](https://schemathesis.readthedocs.io/en/stable/reference/python/).

Встроенный `case.call()` синхронный. Для async-клиента предусмотрена сериализация `case.as_transport_kwargs()`; перенос параметров в testsuite `service_client` нужно проверить. Обычный `@schema.parametrize()` не включает stateful-фазу — есть отдельный `as_state_machine()`. [Async integration](https://schemathesis.readthedocs.io/en/stable/explanations/pytest/#async-support), [stateful API](https://schemathesis.readthedocs.io/en/stable/guides/stateful-testing/).

Function-scoped фикстура выполняется один раз на тест, а не на каждый сгенерированный вход. Подготовка/сброс нужны и при поиске, и при минимизации: shrinking повторно исполняет тест. `hypothesis.target(metric)` позволяет задать числовую цель, но это ещё не адаптер корпуса по новым ветвям C++. [Жизненный цикл примера](https://schemathesis.readthedocs.io/en/stable/guides/hypothesis-strategies/#create-and-clean-up-records-per-case), [targeted testing](https://schemathesis.readthedocs.io/en/stable/guides/targeted/).

## Готовые движки с внутренней обратной связью

| Решение | Реальная обратная связь | Ограничение для userver |
| --- | --- | --- |
| [EvoMaster](https://github.com/WebFuzzing/EvoMaster/tree/666ad9aa30751290f7eee0421e5bdbcdb13459d4#readme) | Инструментирование JVM, покрытие и расстояния до выполнения условий, SQL-эвристики; драйвер управления сервисом | Актуальная white-box поддержка — JVM. Готового C++-инструментирования нет; black-box HTTP доступен независимо от языка |
| [WuppieFuzz](https://github.com/TNO-S3/WuppieFuzz/tree/11256c0075212305ccffd49a5ca5d7e4f53804de) | Stateful OpenAPI-фаззинг на LibAFL, покрытие через внешних агентов; также обратная связь по OpenTelemetry | Для C++ нужен адаптер. Python-проверки и жизненный цикл testsuite не предоставлены готовой интеграцией |
| [AFLNet](https://github.com/aflnet/aflnet) | Покрытие серверного кода и состояния, выводимые из кодов ответов; мутации цепочек сообщений | Требуется протокольная обвязка; JSON Schema, fixture ID и наши ограничения на валидность автоматически не соблюдаются |
| [StateAFL](https://github.com/stateafl/stateafl) | Покрытие кода плюс оценка состояний по снимкам долгоживущих областей памяти | Исследовательский аналог stateful-поиска; не готовая интеграция OpenAPI + testsuite |

EvoMaster интересен архитектурой драйвера: приложение запускается под управлением теста, а `resetStateOfSUT()` восстанавливает его состояние. Автоматизированная очистка SQL не заменяет сброс произвольных полей приложения. [Контракт драйвера](https://github.com/WebFuzzing/EvoMaster/blob/666ad9aa30751290f7eee0421e5bdbcdb13459d4/docs/write_driver.md#independent-tests).

У WuppieFuzz проверен [LCOV-клиент](https://github.com/TNO-S3/WuppieFuzz/blob/11256c0075212305ccffd49a5ca5d7e4f53804de/src/coverage_clients/lcov_client.rs). Он запрашивает данные через TCP-протокол и превращает `file:line` в признаки исполнения. По этому контракту возможно подключить инструментированный C++-сервис через собственный агент без изменения генератора; работоспособность на userver ещё не проверена. В этой версии учитываются строки, а не LCOV branch records или точные hit counts, и карта ограничена 32 768 различными строками. Выгрузить LCOV-файл на диск недостаточно — нужен агент, поддерживающий протокол и границы примеров.

Сброс coverage у WuppieFuzz не сбрасывает БД или память приложения. В проверенных [executor](https://github.com/TNO-S3/WuppieFuzz/blob/11256c0075212305ccffd49a5ca5d7e4f53804de/src/executor.rs) и конфигурации штатного Python before/after callback для произвольного reset не найдено. Для строго валидных по схеме входов также нужно ограничить мутации: существующий движок может изменять методы, пути и связи запросов.

В актуальном WuppieFuzz уже есть feedback по типам spans и связям parent–child. Операции нормализуются по HTTP route/template или RPC method; случайные trace/span ID не определяют новизну. Это множество признаков и рёбер, а не сравнение полного графа. Счётчики вызовов, длительности и состояние отмены в эти признаки не входят. [Определение признаков](https://github.com/TNO-S3/WuppieFuzz/blob/11256c0075212305ccffd49a5ca5d7e4f53804de/src/coverage_clients/otel/coverage.rs).

Трассы приходят асинхронно и связываются с сохранённой последовательностью запросов; завершение HTTP-ответа не означает получение всей трассы. Это важный аналог для проектирования границ наблюдения в userver. [OTel-клиент](https://github.com/TNO-S3/WuppieFuzz/blob/11256c0075212305ccffd49a5ca5d7e4f53804de/src/coverage_clients/otel/client.rs), [trace store](https://github.com/TNO-S3/WuppieFuzz/blob/11256c0075212305ccffd49a5ca5d7e4f53804de/src/coverage_clients/otel/trace_store.rs).

## Инструменты для C++

| Решение | Применимость |
| --- | --- |
| [libFuzzer](https://llvm.org/docs/LibFuzzer.html) | Покрытие, сравнения/value profiling, корпус и минимизация для функции в инструментированном процессе. Подходит для выделенного валидатора или парсера; HTTP-клиент в fuzz target сам по себе не получает покрытие отдельного сервера |
| [FuzzTest](https://github.com/google/fuzztest) | C++ property-based тесты с типизированными доменами, assertions и coverage-guided поиском. Есть protobuf-домены; запуск REST-сервиса, выполнение действий и сброс состояния задаёт автор harness |
| [AFL++](https://aflplus.plus/docs/fuzzing_in_depth/) | Инструментирование C/C++, корпус, мутации, CmpLog. Возможен сетевой адаптер через custom mutator, но управление процессом нужно согласовать с testsuite |
| [libprotobuf-mutator](https://github.com/google/libprotobuf-mutator) | Структурные мутации protobuf и интеграция с libFuzzer. Это библиотека генерации, а не готовый gRPC-фаззер; правила `buf.validate` требуют отдельного учёта |

В AFL++ есть [custom mutators и `fuzz_send`](https://aflplus.plus/docs/custom_mutators/). Persistent mode допускает ограниченное число итераций до перезапуска. Механизмы `AFL_PERSISTENT_RECORD` / `AFL_PERSISTENT_REPLAY` сохраняют и повторяют ограниченную историю входов для целей с накоплением состояния. Это близкий аналог идеи «N запросов → перезапуск → сохранить плохой префикс», но не автоматическое восстановление внешней БД. [Persistent mode](https://github.com/AFLplusplus/AFLplusplus/blob/stable/instrumentation/README.persistent_mode.md).

## Фреймворки сервисов и интеграции фаззеров

Интеграция может быть пользовательским адаптером к тестовому API фреймворка либо набором fuzz targets, которым разработчики проверяют сам фреймворк. Для нашей постановки полезны оба типа, но они решают разные задачи.

**userver + OSS-Fuzz/Honggfuzz.** Уже есть цель `fuzzservice`, запускающая настоящий HTTP-сервис: `DaemonMain`, `MinimalServerComponentList`, `Ping` и `Hello`; ручки `/ping` и `/hello`. Это проверка runtime, HTTP-стека, маршрутизации и простого обработчика. [main.cpp](https://github.com/google/oss-fuzz/blob/1870999a21eb29516b57bbc1d2e043032097f74d/projects/userver/main.cpp), [конфигурация](https://github.com/google/oss-fuzz/blob/1870999a21eb29516b57bbc1d2e043032097f74d/projects/userver/static_config.yaml).

В [project.yaml](https://github.com/google/oss-fuzz/blob/1870999a21eb29516b57bbc1d2e043032097f74d/projects/userver/project.yaml) выбран Honggfuzz. Его [netdriver](https://github.com/google/honggfuzz/blob/6dff0a7e34681b5998ce721f5891f70fc1d92674/libhfnetdriver/netdriver.c) запускает сервер в отдельном потоке и передаёт очередной байтовый вход через сокет. Ветка libFuzzer в `main.cpp` пока содержит TODO и немедленный возврат; считать её работающей альтернативой нельзя. Нет reset прикладного состояния на каждый вход. Существующую [сборку](https://github.com/google/oss-fuzz/blob/1870999a21eb29516b57bbc1d2e043032097f74d/projects/userver/build.sh) можно исследовать как основу instrumented server harness. Конкретная цель не предоставляет OpenAPI/proto-генерацию, Python-проверки или testsuite-окружение с БД/моками. Реальная версия userver в OSS-Fuzz-кампании этой проверкой не установлена: сборка загружает обновляемый исходный репозиторий.

**Spring Boot + Jazzer/CI Fuzz.** У авторов фаззера есть [работающий пример интеграции](https://github.com/CodeIntelligenceTesting/spring-boot-example): `@WebMvcTest`, `MockMvc` и `@FuzzTest`; вход фаззера становится параметром запроса к обработчику. Поиск направляется покрытием JVM. Это близко к желаемому интерфейсу «написать обычный тест ручки и дать фаззеру выбирать данные». `MockMvc` работает внутри процесса, поэтому сетевой HTTP-парсер контейнера этим примером не проверяется. Это внешний пример интеграции, а не встроенный фаззер Spring.

**Spring Boot + EvoMaster.** Другой путь — запустить настоящее приложение через драйвер, предоставив адрес OpenAPI, пакеты для инструментирования, lifecycle и reset. Такой подход ближе к проверке сервиса по настоящему HTTP в testsuite. Привязка к Spring здесь находится в адаптере запуска; методы управления состоянием обязан предоставить автор. [Руководство драйвера](https://github.com/WebFuzzing/EvoMaster/blob/666ad9aa30751290f7eee0421e5bdbcdb13459d4/docs/write_driver.md).

**FastAPI, Flask, Django/DRF + Schemathesis.** Есть документированные адаптеры `from_asgi` / `from_wsgi`, pytest-проверки и взаимодействие с фикстурами. Запрос проходит приложение внутри процесса; для Django описан доступ к БД через pytest-django. В актуальной версии также извлекаются константы из исходников обработчиков как кандидаты входных данных. Это использование знаний о реализации, однако не доказательство мутаций под управлением runtime coverage. [Интеграции Python-приложений](https://schemathesis.readthedocs.io/en/stable/guides/python-apps/).

**Micronaut.** Команда поддерживает [micronaut-fuzzing](https://github.com/micronaut-projects/micronaut-fuzzing) — собственную инфраструктуру фаззинга с Jazzer. HTTP-цели используют встроенный Netty channel. Это пример проверки внутреннего HTTP-стека фреймворка. В harness есть проверки утечек и чрезмерной стоимости CPU; наличие такой проверки само по себе не означает, что CPU используется для выбора следующего входа. [Базовый harness](https://github.com/micronaut-projects/micronaut-fuzzing/blob/8de52effcdee25003a631f29db844441d3744e8c/fuzzing-tests/src/main/java/io/micronaut/fuzzing/EmbeddedChannelFuzzerBase.java).

**Go `net/http`.** Стандартные `testing.F` / `go test -fuzz` дают coverage-guided fuzzing; `httptest` позволяет вызвать handler напрямую или поднять локальный HTTP-сервер. Их можно соединить собственным harness. Генерацию OpenAPI-входов и восстановление состояния нужно добавить; это составление стандартных API, а не готовый специализированный REST-фаззер. [Go fuzzing](https://go.dev/doc/security/fuzz/), [httptest](https://pkg.go.dev/net/http/httptest).

**Crow, C++.** В upstream есть fuzz targets и их CMake-сборка. [HTTP target](https://github.com/CrowCpp/Crow/blob/4a701c519a42414fabf425e0a67f35a167b1185d/tests/fuzz/http_fuzzer.cpp) разбирает HTTP-вход и вызывает `app.handle_full(parser.req, res)`: проверяются также маршрутизация и фиксированные обработчики. Это содержательный пример фаззинга C++-фреймворка; общего интерфейса OpenAPI + произвольный пользовательский сервис + DB fixtures в проверенных целях не обнаружено. [Сборка целей](https://github.com/CrowCpp/Crow/blob/4a701c519a42414fabf425e0a67f35a167b1185d/tests/fuzz/CMakeLists.txt).

## Обратная связь userver сверх покрытия

Ниже — предложения для экспериментов, а не существующий API фаззинга. В coverage-guided режиме полезно сохранять множество новых ветвей/рёбер, а не только общий процент покрытия. Дополнительные сигналы должны находить различия между исполнениями, проходящими через уже известный код.

| Сигнал | Как направляет поиск | Откуда получить и что потребуется |
| --- | --- | --- |
| Состояния отмены и Deadline Propagation | Новые сочетания: истечение дедлайна до входа в ручку, при ожидании соединения, во время downstream-запроса, при завершении дочерней задачи | Уже есть метрики и span tags DP; точный этап и причинную связь с задачами нужно наблюдать через testpoints/дополнительные события |
| Вызовы зависимостей | Новые типы операций/связей; необычный fan-out, повторные запросы, retry/fallback; дорогой вход при той же ветви кода | Трассы, счётчики моков, при необходимости события клиентских обёрток. Нормализовать IDs и значения параметров |
| Работа корутин и ожидания ресурсов | Новые диапазоны числа порождённых задач, очереди, ожидания соединения; работа, пережившая запрос | Есть общие метрики `tasks.created`, `alive`, `queued`, `running`, `finished`; для надёжного per-case feedback нужны привязка к примеру и контроль фоновой работы |
| Состояния Congestion Control | Новые переходы между режимами ограничения/восстановления и их сочетания с дедлайнами | Есть `congestion-control.rps.current-state` и счётчики состояний. Нужны управляемая нагрузка, настройки и наблюдение переходов во времени |
| Прикладные состояния | Новый результат «cache miss → заполнение → hit», версия/категория содержимого кеша, переход бизнес-объекта | Метки/testpoints автора теста. Смысл приватного `RcuMap` автоматически неизвестен |
| Стоимость обработки | Сохранение входов с растущим числом DB/downstream-операций, задач или аллокаций при ограниченной длине входа | Предпочитать измеримые счётчики; CPU/latency шумны и требуют повторения и фиксированного окружения |

Доступные основы подтверждены документацией: [метрики движка](https://userver.tech/d9/dac/md_en_2userver_2service__monitor.html), [DP](https://userver.tech/d6/d64/md_en_2userver_2deadline__propagation.html), [CC](https://userver.tech/d0/d44/md_en_2userver_2congestion__control.html), [трассировка](https://userver.tech/df/d0c/md_en_2userver_2logging.html), [testpoints и метрики в testsuite](https://userver.tech/df/d07/md_en_2userver_2functional__testing.html). Они обеспечивают наблюдение, но ещё не привязку всех событий к одной итерации фаззера.

Для начального REST-прототипа достаточно попробовать число обращений к мокам и 1–2 явно заданные метки состояния. Для отдельного эксперимента с DP перспективны этап отмены и завершение связанных задач. Сигналы CC требуют более сложных сценариев; не стоит включать их все в первый этап.

Пример полезного состояния: запрос с коротким дедлайном породил несколько дочерних операций, одна ждала соединение, затем пришла отмена. Новый HTTP-статус и новое покрытие при этом могут отсутствовать. Фаззер сохраняет такую комбинацию и меняет входы/управляемые условия рядом с ней. Отдельная проверка определяет, завершились ли обязанные завершиться операции и не произошёл ли запрещённый побочный эффект.

Сигнал интересности не равен ошибке. Истёкший дедлайн, высокая очередь или cache miss могут быть нормальны. Проверка нарушения должна задавать контракт: например, конкретная операция обязана завершиться за допустимое время после отмены. В userver существуют разрешённые фоновые действия после отмены, поэтому требовать немедленного отсутствия вообще всех задач неправильно.

Практические правила для адаптера:

- Каждому примеру/цепочке присваивается ID; известны начало наблюдения, конец запроса и завершение относящейся к нему работы. Потомки, утратившие контекст, требуют отдельного учёта.
- Метрики до/после — дешёвый прототип, но фоновые задачи и сам мониторинг могут искажать разность. Gauge после ответа не показывает пиковую очередь и пропущенные переходы.
- Состояния описываются небольшими категориями и переходами; числа — диапазонами. Случайные IDs, адреса, timestamps и полные дампы кеша не считаются новой полезной ситуацией сами по себе.
- Не сводить всё к «максимизировать число задач/время»: ограничить размеры входов и длину сценария, иначе поиск выиграет простым увеличением нагрузки. Полезные счётчики можно оптимизировать раздельно.
- Сбои воспроизводятся на восстановленном окружении; сомнительные временные эффекты перепроверяются. Пользовательский reset должен действовать и во время минимизации.

Предшествующие работы уже исследуют feedback сверх покрытия: [IJON](https://github.com/RUB-SysSec/ijon) использует аннотации состояния, [PerfFuzz](https://github.com/carolemieux/perffuzz) — многомерные счётчики стоимости, StateAFL — состояния памяти, WuppieFuzz — признаки трасс. Возможный вклад проекта — недорогие, устойчивые и полезные признаки именно userver и их доступность через testsuite, с экспериментальным подтверждением.

## Направленный поиск и цели автора теста

Directed fuzzing полезен, когда известно, какое место или поведение нужно исследовать: изменённая логика кеша, подозрительный testpoint, отмена во время ожидания ресурса. Вместо поиска любого нового поведения бюджет направляется к этой цели. Обнаружение ошибки по-прежнему требует отдельной проверки.

В [AFLGo](https://github.com/aflgo/aflgo) цель задаётся расположением в исходниках. Инструмент строит графы вызовов и потока управления, вычисляет расстояния до целей и использует их при распределении усилий поиска. В руководстве есть прямой пример извлечения целей из изменённых строк коммита для patch testing. Это существующий подход, а его подключение к современному userver потребует отдельной проверки инструментирования и сборки.

Для нашего интерфейса предлагаются три понятия, без фиксации синтаксиса API:

| Понятие | Пример |
| --- | --- |
| Ограничения входов | JSON валиден; ID берётся из фикстуры; в цепочке не более N запросов |
| Цель и прогресс | Дойти до события «запрос ожидает соединение с БД» и добиться истечения дедлайна во время этого ожидания; сохранить входы, достигающие промежуточных этапов |
| Проверяемое свойство | После отмены конкретное ожидание завершается в пределах допуска и не выполняется запрещённое контрактом действие |

Один флаг `target_reached` ещё не даёт направления до первого попадания в цель. Для труднодостижимого поведения нужны промежуточные события, числовая оценка приближения, начальные примеры или более глубокая инструментация. Пользовательские числовые цели уже поддерживаются через [Hypothesis target](https://hypothesis.readthedocs.io/en/latest/reference/api.html#hypothesis.target); пригодность такого механизма для нашего поиска требуется измерить.

Проверка достижимости должна быть видна в результате: «цель не достигнута за бюджет» не равнозначно успешной проверке поведения в целевом состоянии. При сокращении репродуктора целевого нарушения сохраняются нужное достижение цели и нарушение свойства. Общие проверки падений и контрактов продолжают действовать и вне цели. Условия генерации, reset и фикстуры действуют при всех повторных исполнениях.

Если обычный testsuite-сценарий уже гарантирует попадание в нужное состояние, сначала достаточно фаззить данные внутри этого сценария. Directed-поиск оправдан, когда до цели трудно дойти или нужно распределять ограниченный бюджет между многими направлениями. Сигнал должен реально влиять на отбор и мутации входов; простая запись метрики этого не обеспечивает. Часть бюджета можно сохранять для общего исследования покрытия.

Направление по диффу можно развивать поэтапно: сначала выбирать из накопленного корпуса тесты, покрывающие изменённые функции; затем уделять больше мутаций таким входам; позднее подключить вычисление расстояний до ещё не достигнутых изменённых участков. Первые два шага используют связи покрытия с изменениями, но не обеспечивают полноценный directed search до неизвестной области. Удалённые строки, изменения конфигурации и косвенно затронутое поведение требуют отдельной обработки. Достижение изменённой строки не доказывает корректность изменения.

Для C++-сервиса статическое расстояние по графу также не описывает всё поведение: переход через корутину, callback или зависимость может потребовать состояния окружения и определённого порядка событий. Это ограничение предлагаемого применения, которое следует проверять на конкретных целях. Если фаззер меняет только JSON, он не может произвольно управлять расписанием задач; соответствующие параметры должны быть явно доступны через сценарий и testsuite.

Для горизонта в шесть месяцев предлагается предусмотреть расширяемые пользовательские цели и проверить одну цель на наблюдаемых событиях userver. Автоматический анализ диффа и собственный аналог AFLGo пока оставить отдельным расширением. Эксперимент сравнивает время/долю достижения цели и обнаружение известных дефектов при одинаковом бюджете; просто больший score не является достаточным результатом.

## Что проверить до выбора архитектуры

1. **Совместимость Python-интерфейса.** Одна REST-ручка, positive generation Schemathesis, дополнительное условие, отправка через `service_client`, проверка ответа/БД. Контрольный дефект должен обнаруживаться, воспроизводиться и минимизироваться при выбранном reset.
2. **Настоящий C++ feedback.** Небольшой адаптер покрытия и сравнение с WuppieFuzz: корректная привязка данных к цепочке, полнота карты, скорость, ограничения на мутации и владение процессом. Этот эксперимент не требует заранее выбирать собственный движок.
3. **Польза знаний userver.** На одном генераторе сравнить: без внутренней обратной связи; только coverage; coverage плюс выбранные семантические признаки. Одинаковые бюджеты, несколько запусков, известные дефекты, воспроизводимость и накладные расходы.
4. **LLM после базового сравнения.** Добавлять модель отдельно, чтобы вклад новых сигналов и вклад генерации LLM можно было измерить независимо.

Schemathesis/Hypothesis и WuppieFuzz — кандидаты с разными сильными сторонами. Их совместимость и объединение в один цикл поиска не предполагаются автоматически. Сначала нужно выбрать, кто владеет генерацией, корпусом, минимизацией и жизненным циклом сервиса.
