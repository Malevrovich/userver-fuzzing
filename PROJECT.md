# Grey-box фаззинг для userver

Рабочее описание магистерского проекта. Горизонт — примерно шесть месяцев.
Границы уточняются; реализация и эксперименты в рамках этого описания ещё не выполнены.

## Цель и идея

Создать удобный инструмент grey-box фаззинга сервисов на C++-фреймворке userver, интегрированный с testsuite. Он должен искать проблемные входы: от одного необычного запроса до сочетаний запросов и условий исполнения, приводящих к падениям, зависаниям (в том числе дедлокам) и нарушениям контрактов. Область применения охватывает протокольный слой, пользовательские обработчики REST/gRPC и механизмы фреймворка. OpenAPI и proto — обязательные, но не единственные рассматриваемые источники входных данных.

Инструмент должен генерировать и изменять входы, использовать обратную связь из сервиса для направления поиска и сохранять обнаруженные сбои для воспроизведения.

В userver уже есть [OSS-Fuzz-интеграция](https://github.com/google/oss-fuzz/tree/1870999a21eb29516b57bbc1d2e043032097f74d/projects/userver): Honggfuzz запускает настоящий HTTP-сервис с ручками `/ping` и `/hello`. Проект развивает поддержку фаззинга на уровне прикладных сервисов: схемы запросов, Python-тесты, БД и моки, пользовательские свойства, управление состоянием и обратная связь из runtime.

Способ реализации серверной ручки не должен влиять на возможность подключения фаззера: поддерживаются обработчики, написанные вручную и созданные через кодген. Интеграция опирается на описание API и testsuite-окружение, без обязательной зависимости от конкретного генератора или сгенерированных классов обработчика. Для ручки, написанной вручную, JSON Schema/OpenAPI можно предоставить отдельно; схема не обязана участвовать в генерации серверного кода.

Testsuite и пользовательский Python-интерфейс — обязательные части первого прототипа. Используется существующая инфраструктура запуска сервиса, тестовой БД, подготовки данных и моков. Разработчик может задать условия на генерируемый запрос и написать собственную проверку ответа. Проверяются отдельные запросы либо ограниченные цепочки запросов с накоплением состояния; генерация сложных бизнес-сценариев рассматривается как дальнейшее расширение.

Практическая цель — упростить подключение фаззинга разработчиками userver-сервисов. Автор работает в команде фреймворка и может организовать пилоты на реальном коде и собрать обратную связь пользователей.

## Первый этап: валидные JSON-входы в testsuite

Проверить, способна ли выбранная REST-ручка корректно обработать разнообразные входы, допустимые её JSON Schema. Начать с одной ручки и существующего testsuite-окружения. Целевое свойство относится ко всем допустимым входам; конечный запуск ищет контрпримеры и не доказывает полный перебор.

1. Testsuite запускает сервис и тестовую БД, готовит исходные данные и моки зависимостей.
2. Генератор строит JSON-тело по схеме с учётом дополнительных условий Python-теста, включая граничные значения и сочетания полей. Тело каждого отправляемого примера должно проходить валидацию; метод, URL, параметры и заголовки задаются описанием запроса и testsuite-окружением.
3. Перед каждой единицей фаззинга — отдельным запросом или целой цепочкой — обеспечивается заданное исходное состояние БД, моков и сервиса выбранным режимом изоляции. Внутри цепочки состояние сохраняется. Если много примеров исполняются внутри одного pytest-теста, восстановление состояния нужно организовать отдельно от фикстур, выполняемых один раз на тест.
4. Запрос отправляется через обычный HTTP-клиент testsuite. Проверяются завершение обработки, отсутствие падения и соблюдение согласованного контракта ответа, включая пользовательские проверки на Python.
5. Для найденного нарушения сохраняются полный запрос (включая прикладные заголовки), схема, настройки и данные, необходимые для повторения в том же testsuite-окружении.

JSON Schema тела не описывает HTTP-заголовки автоматически. Полный вход включает метод, URL с параметрами, заголовки и тело. В OpenAPI обычные заголовки запроса описываются через `parameters` с `in: header` и собственной схемой значения; авторизация и тип содержимого описываются отдельными средствами OpenAPI. [Спецификация OpenAPI](https://spec.openapis.org/oas/v3.1.1.html#parameter-object).

При отдельно переданной JSON Schema остальные части запроса задаются через настройки теста и фикстуры testsuite. В первом прототипе допустимо генерировать только тело с подготовленными заголовками. Генерация значений выбранных прикладных заголовков — отдельная возможность с явно заданными ограничениями; служебное оформление HTTP остаётся клиенту. Изменение допустимых значений заголовков не требует повреждения протокола.

Валидность по JSON Schema не гарантирует выполнения бизнес-условий: например, числовой ID может отсутствовать в БД. Предусмотренный контрактом отказ, включая 4xx, считается корректной обработкой. Для проверки успешных веток нужны соответствующие фикстуры и подбор значений из подготовленных данных с сохранением валидности по схеме.

Первый этап замыкает цикл «генерация → окружение → запрос → проверка → воспроизведение». Этот цикл должен стать основой grey-box режима с обратной связью по покрытию C++. Режим с отключённой обратной связью нужен для сравнения; сам по себе он не считается grey-box. LLM расширяет генерацию при остановке прогресса.

## Пользовательский Python-интерфейс

Разработчик пишет асинхронный тест с фикстурами testsuite и задаёт:

- схему и дополнительные условия генерации — например, `min_price <= max_price` или выбор ID из подготовленных данных БД;
- отправку запроса с нужными параметрами и заголовками;
- собственные проверки результата через Python-код и `assert`: статус, содержимое ответа, при необходимости состояние БД или наблюдаемые события.

Схема и условия определяют область входов, а проверки результата определяют нарушения. Дополнительные условия сужают область конкретного теста; это должно быть явно отражено в его описании и результатах. Обычная генерация, мутации и предложения LLM проходят одни и те же проверки допустимости. Невозможность получить допустимые примеры должна быть видна в результате запуска.

Цикл поиска и сбор обратной связи остаются ответственностью инструмента. Подготовка состояния перед каждым примером должна быть явно предусмотрена интерфейсом; конкретный синтаксис API ещё предстоит выбрать.

Рассматривается дополнительная возможность задавать цель поиска: достижение testpoint, выбранного состояния или сочетания событий, а также оценку приближения к цели. Цель отделяется от проверки корректности: дойти до отмены во время ожидания БД ещё не означает найти ошибку. Автоматический выбор целей по диффу и вычисление расстояний по графу C++-кода — отдельное возможное расширение, пока не обязательная часть проекта.

## Изоляция и накопление состояния

Общий сброс testsuite не гарантирует очистку произвольной памяти сервиса: например, `RcuMap` может быть приватным полем обработчика. Предусматриваются два режима:

1. **Пользовательский сброс.** Автор задаёт функцию восстановления состояния между примерами. Python управляет БД и моками; для полей C++-обработчика нужен сервисный callback. В userver уже есть [testsuite::RegisterCacheResetter](https://github.com/userver-framework/userver/blob/285119a40d885c92b0254d6973bc9f035ddc181b/core/include/userver/testsuite/cache_control.hpp#L223), позволяющий зарегистрировать такой сброс. Автор отвечает за его полноту; прежде чем сбрасывать состояние, нужно завершить работу предыдущего примера, которая может его снова изменить.
2. **Цепочки с перезапуском.** Запускается сервис с подготовленным окружением, выполняется до N запросов, затем сервис перезапускается. Состояние внутри цепочки намеренно накапливается. При нарушении сохраняются вся цепочка до сбоя и контекст запуска; воспроизведение начинается с исходного состояния. N = 1 даёт вариант с новым процессом на каждый запрос. Сокращать репродуктор нужно проверкой всей оставшейся последовательности на свежем окружении.

Перезапуск очищает память C++-процесса, включая приватный `RcuMap`, но отдельно требуется восстановить БД, моки, изменяемое состояние Python-теста и используемые файлы. Сначала завершается предыдущая работа, затем восстанавливается внешнее окружение и запускается новый процесс. Обработчики моков должны оставаться доступны до завершения остановки сервиса. Нельзя считать ошибку только последнего запроса независимой от предыдущих запросов цепочки.

Журнал цепочки содержит фактические запросы, значимые результаты и действия окружения, исходные фикстуры и конфигурацию. Одного seed недостаточно для воспроизведения. При появлении параллельности отдельно учитываются порядок событий и повторяемость находки. Покрытие собирается в границах запроса или цепочки после подготовки окружения; глобальный корпус сохраняется между перезапусками.

Начальные механизмы уже существуют: [uservice_oneshot](https://userver.tech/df/d07/md_en_2userver_2functional__testing.html) перезапускает сервис на границе pytest-теста, а reset-hooks позволяют сбрасывать зарегистрированное состояние. Плагину фаззера нужен жизненный цикл на уровне примера/цепочки. Возможные доработки userver — управляемое завершение работы примера, диагностика оставшихся задач и границы сбора покрытия; необходимость определяется прототипом. Новый универсальный сброс всех полей обработчика не предполагается.

## Вход и обнаружение ошибок

Предлагается поддержать входы разной сложности: отдельный запрос, последовательность запросов и запросы с управляемыми условиями — дедлайнами, ответами и задержками зависимостей, при необходимости ограниченной параллельностью. Для повторения сохраняются входные данные и необходимый контекст запуска; воспроизводимость конкурентных сбоев нужно проверять отдельно.

Общее направление — генерация структурированных вызовов по OpenAPI/proto и отправка через обычные HTTP/gRPC-клиенты. Первый этап ограничен JSON-входами, валидными по схеме REST-ручки. Проверка входов за пределами схемы может рассматриваться позднее. Намеренное повреждение протокольного представления HTTP/1, HTTP/2 и gRPC исключено из текущего объёма.

Полезность входа определяется результатом запуска: новым покрытием, новым наблюдаемым состоянием или обнаруженным нарушением. Рост покрытия помогает направлять поиск, а ошибки определяются отдельными проверками:

- падение процесса, срабатывание санитайзера или assertion;
- отсутствие ожидаемого прогресса в пределах заданного времени — кандидат на зависание, требующий повторения и диагностики, а не доказанный дедлок;
- нарушение явно заданного свойства сервиса или фреймворка.

Для свойства «запрос должен остановиться» нужно определить, какая операция обязана завершиться, где ожидается обработка отмены, допустимое время завершения и разрешённые фоновые действия. Один код HTTP-ответа или факт истечения таймаута клиента этого не доказывает. Интерфейс включает базовые встроенные проверки и дополнительные свойства, задаваемые разработчиком через testsuite.

## Область применения

- **Протокольный слой:** обработка HTTP/1 и HTTP/2 в userver на путях, достижимых через обычные клиентские запросы; в текущем объёме — без намеренного повреждения протокольных сообщений.
- **Пользовательские обработчики:** необычные значения, сочетания параметров, граничные случаи и ошибки прикладной обработки REST/gRPC-запросов.
- **Взаимодействия и механизмы фреймворка:** последовательности и конкурентная обработка запросов, поведение зависимостей, Deadline Propagation и Congestion Control.

Это общая область развития после первого этапа. Покрытие C++-кода — исходный кандидат для обратной связи; состояния механизмов, очередей и задач — возможное расширение. Отдельный пользовательский C++ API остаётся открытым решением.

## Кандидат для gRPC-этапа: grpc-protovalidate

В [grpc-protovalidate](https://github.com/userver-framework/userver/tree/285119a40d885c92b0254d6973bc9f035ddc181b/libraries/grpc-protovalidate) есть обёртка над `protovalidate-cc` для использования с корутинами и middleware для проверки запросов и ответов. Реализация и существующие тесты просмотрены по исходникам; фаззинг и сборка не запускались.

Предлагаемый стенд — небольшой gRPC-сервис с включённым валидатором, генерация protobuf-сообщений и пользовательские проверки на Python через testsuite. Проверяются граничные значения, отсутствие полей, вложенные сообщения, коллекции и сочетания ограничений. Для этого примера нужны как сообщения, удовлетворяющие аннотациям `buf.validate`, так и сообщения, нарушающие их, но корректные по структуре protobuf. Это отдельное расширение после первого REST-этапа и не требует повреждения протокола.

Проверяемые свойства: допустимый запрос проходит в обработчик; нарушающий правила отклоняется с ожидаемым статусом без вызова обработчика; `fail-fast` сохраняет решение о допустимости, меняя объём диагностики; `send-violations` управляет деталями ошибки. Проверку ответов можно исследовать через управляемый gRPC-мок зависимости. При проверке серверного валидатора отправляющий клиент должен пропускать сообщения с нарушениями правил до сервера.

Ожидаемые результаты задаются независимыми Python-проверками простых правил, существующим [conformance-набором Protovalidate](https://github.com/bufbuild/protovalidate/blob/main/docs/conformance.md) или сравнением с другой реализацией при совместимых закреплённых версиях. Python `protovalidate` 2.0 сам использует C++-ядро и не является независимым эталоном этого ядра; для такого сравнения можно исследовать реализацию на Go. [Описание Python 2.0](https://buf.build/blog/faster-protovalidate).

## Исследовательская часть

Обзор существующих REST-фаззеров, интеграций с сервисными фреймворками и кандидатов на обратную связь сверх покрытия вынесен в [RESEARCH.md](RESEARCH.md). Предварительные кандидаты для экспериментов — Schemathesis как источник структурированных входов для Python-тестов и WuppieFuzz как готовый grey-box REST-движок. Выбор основы ещё не сделан; совместимость с testsuite требует прототипа.

Планируется обращаться к LLM, когда фаззер перестаёт находить новое покрытие или новые состояния. Роль модели — предлагать новые перспективные входные данные для дальнейшего фаззинга. Их полезность проверяется исполнением и обратной связью; подходящие кандидаты пополняют корпус, сбои сохраняются отдельно. Состав доступного модели контекста и критерий остановки прогресса ещё предстоит выбрать.

Предлагаемые проверяемые гипотезы:

1. Обратная связь из userver помогает находить нарушения свойств эффективнее, чем тот же генератор без неё.
2. Обращение к LLM при остановке прогресса улучшает результаты относительно продолжения обычного поиска при сопоставимом бюджете.
3. Контекст userver/testsuite повышает полезность предложений LLM относительно использования только схемы API и примеров запросов.
4. Семантические события userver — состояния отмены, обращения к зависимостям и переходы между состояниями — улучшают поиск относительно обратной связи только по покрытию при одинаковом бюджете. Этот эффект нужно проверять отдельно от эффекта LLM.

Последняя гипотеза — кандидат для сужения исследовательской темы. Само сочетание фаззинга и LLM не является новым: ChatAFL уже использует модель для выхода с плато покрытия. Аналогично, coverage-guided REST-фаззинг существует в WuppieFuzz. Конкретный вклад проекта нужно определить после обзора аналогов.

## Предлагаемая оценка результата

Сравнивать режимы с отключёнными отдельными возможностями на одинаковых стендах и начальных корпусах, с повторными запусками и одинаковым бюджетом времени, включая ожидание LLM. Для LLM дополнительно учитывать число вызовов и стоимость; полезный контроль — обновление корпуса без модели при том же критерии остановки прогресса.

Основные показатели: доля обнаруженных известных дефектов, время до их обнаружения, покрытие во времени, воспроизводимость сбоев и накладные расходы. Удобство интеграции оценивать отдельно на пилотах. Проверяемые свойства и способ сброса состояния между примерами должны быть определены до экспериментов.

Совместимость проверить на обоих вариантах серверной реализации: ручном обработчике и обработчике с кодгеном, подключённых через общий интерфейс фаззера.

Полезный результат — работающая интеграция, воспроизводимые эксперименты на специально внесённых дефектах и оценка применимости на реальных сервисах. Обнаружение новых ошибок желательно, но не является обязательным условием успеха. Превосходство отдельных режимов предстоит проверить экспериментально.

## Открытые решения

- Конкретная REST-ручка, её JSON Schema, параметры и заголовки запроса, исходные данные БД и допустимые ответы для первого прототипа.
- Конкретная форма Python API для условий генерации, пользовательских проверок и подготовки состояния перед примером.
- Порядок дальнейших расширений: gRPC/proto, сценарии, мутация окружения и параллельность.
- Глубина инструментации, управление состоянием и воспроизведение временных событий.
- Контекст, доступный LLM, критерий остановки прогресса и центральная исследовательская гипотеза.
