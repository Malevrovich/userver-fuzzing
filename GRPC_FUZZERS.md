# Шорт-лист фаззеров для gRPC

Зафиксирован 29 октября 2026 года. Это кандидаты для проб на тестовом стенде;
запуски и интеграции ещё предстоят. Соседний список — [REST](REST_FUZZERS.md),
постановка — [PROJECT.md](PROJECT.md).

Здесь важно различать фаззинг сервиса и генерацию protobuf-сообщений.
Генератор сообщений сам по себе не отправляет RPC, не ищет порядок вызовов,
не перезапускает сервер и не проверяет его состояние. В список включены как
инструменты для API, так и библиотеки, для которых мы готовы написать обвязку.

## Кандидаты

| Проект | Роль и режим для нашего стенда | Зачем пробовать и что потребуется |
| --- | --- | --- |
| [EvoMaster](https://github.com/WebFuzzing/EvoMaster) | RPC API testing, black-box | Основной кандидат на системный поиск ошибок. RPC-режим требует собственного JVM-драйвера и клиентских stubs, в том числе при black-box-тестировании C++-сервиса. Это не запуск напрямую по `.proto`; совместимость драйвера с нашим сервисом надо проверить. |
| [Viasat/gRPC-Fuzzer](https://github.com/Viasat/gRPC-Fuzzer) | Небольшой Python black-box-инструмент | Использует ProtoFuzz для входов. Для своего сервиса нужно написать клиент по его protobuf API. Стоит попробовать как простой специализированный вариант; проект давно не обновлялся, совместимость с текущими protobuf/grpcio и поддержку цепочек заранее не предполагаем. |
| [Hypothesis](https://github.com/HypothesisWorks/hypothesis) + protobuf-стратегии | Библиотека для Python/testsuite, black-box | Генерация полей protobuf, stateful-сценариев и сокращение найденных примеров. Мы задаём стратегии, отправку через gRPC-клиент, перенос значений между вызовами, проверки и сброс окружения. Удобный контрольный вариант для желаемого интерфейса на Python. |
| [ProtoFuzz](https://github.com/trailofbits/protofuzz) | Генератор protobuf для Python | Получает описание protobuf и генерирует сообщения; поддерживает пользовательские зависимости между полями. Нужна собственная обвязка для RPC, цепочек, проверки результатов и воспроизведения. Это компонент для сравнения генераторов, а не готовый coverage-guided фаззер сервиса. |
| [libprotobuf-mutator](https://github.com/google/libprotobuf-mutator) + [libFuzzer](https://llvm.org/docs/LibFuzzer.html) | Структурные мутации + grey-box-движок | Вариант с собственной C++-обвязкой: protobuf описывает один вход либо последовательность действий, libFuzzer направляет поиск по покрытию. Для отдельного серверного процесса нужна специальная интеграция обратной связи; инструментация одного клиента не даёт покрытие серверных обработчиков. Подключение Python/testsuite также потребует работы. |

Уточнения к сравнению:

- **EvoMaster:** [RPC-драйверы](https://github.com/WebFuzzing/EvoMaster/blob/master/docs/write_driver.md#rpc-apis),
  [black-box режим](https://github.com/WebFuzzing/EvoMaster/blob/master/docs/blackbox.md).
  JVM-клиент может обращаться к C++-сервису. White-box-инструментацию JVM
  из этого не переносим на сервер C++.
- **Hypothesis:** [stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html).
  Для маленького стенда стратегии можно написать вручную. Сторонние
  protobuf-адаптеры перечислены в [документации](https://hypothesis.readthedocs.io/en/latest/strategies.html),
  но их совместимость ещё не проверена. Python-генерация без серверной
  обратной связи остаётся black-box.
- **ProtoFuzz и gRPC-Fuzzer:** сравниваем затраты на интеграцию и качество
  генерации, учитывая их общую основу. Это не два независимых движка поиска.
- **libprotobuf-mutator:** мутация protobuf сохраняет структуру сообщения,
  но не гарантирует бизнес-ограничения и правильный порядок RPC. Их задаёт
  обвязка. Наличие исходников C++ не превращает такой запуск в символический
  white-box-анализ.

## На чём сравнивать

Стенд — [simple-grpc-target-service](services/simple-grpc-target-service/README.md),
контракт — [targets.proto](services/simple-grpc-target-service/proto/fuzzing/targets.proto).
Прикладные методы сейчас unary; streaming — отдельное возможное расширение.

| RPC в `TargetService` | Что должен обнаружить инструмент |
| --- | --- |
| `StatelessCrash` | Вход, завершающий процесс |
| `StatelessError` | Неожиданный `INTERNAL` при живом процессе |
| `Sequence` | Последовательность вызовов одного метода, завершающая процесс |
| `Prepare` + `Commit` | Цепочка с передачей ticket и повторным вызовом |
| `DependencyCrash` | Сбой при сочетании входа и ответа `DecisionService` |

Ограничения полей текущего стенда описаны комментариями в `.proto` и
проверяются приложением. Обычный protobuf-генератор не обязан понимать
«обязательное поле», диапазон `[0, 100]` или формат ticket из комментария.
Для сравнения на допустимых входах эти ограничения задаём явно и одинаково
для всех кандидатов. Отдельно учитываем отказы `INVALID_ARGUMENT` и
`FAILED_PRECONDITION`: сами по себе они не означают найденную ошибку.

## Порядок и правила экспериментов

1. Оценить EvoMaster RPC black-box и объём JVM-драйвера для нашего `.proto`.
2. Сделать контрольный Python-вариант на Hypothesis; отдельно попробовать
   gRPC-Fuzzer и ProtoFuzz с учётом общей основы и написанной обвязки.
3. libprotobuf-mutator + libFuzzer оставить для этапа с серверным покрытием
   и специально подготовленным harness — кодом, исполняющим один вход фаззера.

Сравниваем обнаружение каждого сценария, время и число RPC до находки,
воспроизводимость полной цепочки, сокращение примеров и стоимость интеграции.
Используем повторные запуски с одинаковыми бюджетами и начальным состоянием;
общие правила учёта подсказок и репродукторов — в [REST-списке](REST_FUZZERS.md).

Падение подтверждаем завершением процесса: `UNAVAILABLE` у клиента может
означать и обычную сетевую ошибку. `INTERNAL` и дедлайны учитываем отдельно,
по контракту конкретного сценария. Для `DependencyCrash` сначала фиксируем
одинаковый ответ зависимости; генерация ответов моков — отдельный эксперимент.
Внутри цепочки состояние сохраняем, между независимыми примерами восстанавливаем.
