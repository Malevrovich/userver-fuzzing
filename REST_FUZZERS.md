# Шорт-лист фаззеров для REST

Зафиксирован 29 октября 2026 года. Это кандидаты для сравнения на тестовом
стенде; результаты запусков пока не получены, основа собственного инструмента
не выбрана. Соседний список — [gRPC](GRPC_FUZZERS.md), постановка — [PROJECT.md](PROJECT.md).

Цель — проверить поиск ошибок в отдельных запросах и последовательностях
вызовов. Пользовательские тесты собственного инструмента предполагаются на
Python в testsuite. Язык реализации фаззера сам по себе не ограничение:
поддержка C++ нужна там, где мы получаем обратную связь из сервиса.

## Кандидаты

| Проект | Режим для нашего стенда | Зачем пробовать и что потребуется |
| --- | --- | --- |
| [Schemathesis](https://github.com/schemathesis/schemathesis) | Black-box, OpenAPI | Генерация структурированных запросов, проверки ответов, сокращение найденных примеров. Stateful-режим строит цепочки с передачей данных между операциями. Удобный кандидат для сравнения с Python/testsuite; адаптацию асинхронного клиента и сброс состояния между примерами нужно проверить отдельно. |
| [RESTler](https://github.com/microsoft/restler-fuzzer) | Black-box, OpenAPI | Поиск последовательностей запросов с зависимостями producer–consumer: например, создать ресурс и использовать полученный ID. Интересен прежде всего для сценариев с состоянием и ticket. Нужно проверить выведенные зависимости, настроить словари и полноценный режим `fuzz`; один `fuzz-lean` не заменяет поиск длинных цепочек. |
| [EvoMaster](https://github.com/WebFuzzing/EvoMaster) | **Black-box**, OpenAPI | Отдельный обязательный кандидат для эксперимента: генерация API-тестов и поиск сбоев без инструментации сервера. C++-сервис доступен по HTTP независимо от языка реализации. White-box-возможности для JVM не считаем доступными на нашем стенде. |
| [WuppieFuzz](https://github.com/TNO-S3/WuppieFuzz) | Сначала black-box; затем grey-box с адаптером | Фаззер на LibAFL с OpenAPI и мутациями последовательностей. Без покрытия сервера использует обратную связь по endpoint/ответам. Для отдельного grey-box-эксперимента нужен сбор покрытия C++: готовый C++-агент в проверенном наборе не найден. Возможность подключить свой агент через LCOV требует прототипа. |
| [RestTestGen / DeepREST](https://github.com/SeUniVr/RestTestGen) | Black-box, OpenAPI | DeepREST изучает порядок операций и неявные зависимости через обучение с подкреплением. Кандидат на сравнение обнаружения цепочек, которые не полностью заданы связями в схеме. DeepREST доступен в репозитории RestTestGen; подготовку окружения и сброс состояния нужно организовать отдельно. |
| [Hypothesis](https://github.com/HypothesisWorks/hypothesis) + обвязка testsuite | Black-box, Python | Контрольный вариант с генерацией значений, stateful-правилами и сокращением примеров. HTTP-вызовы, допустимые действия, проверки и восстановление окружения задаём сами. Это библиотека property-based testing, поэтому затраты на обвязку учитываем отдельно от готовых API-фаззеров. |

Уточнения к сравнению:

- **Schemathesis:** [stateful testing](https://schemathesis.readthedocs.io/en/stable/guides/stateful-testing/)
  использует связи между операциями. Наличие такого режима не гарантирует
  обнаружения произвольной скрытой последовательности.
- **RESTler:** [режимы поиска](https://github.com/microsoft/restler-fuzzer/blob/main/docs/user-guide/Fuzzing.md).
  Генерация клиентской грамматики допустима: запрет на кодген относится к
  реализации ручек тестового REST-сервиса.
- **EvoMaster:** [black-box режим](https://github.com/WebFuzzing/EvoMaster/blob/master/docs/blackbox.md).
  В первом сравнении используем именно его.
- **WuppieFuzz:** [агенты покрытия](https://github.com/TNO-S3/WuppieFuzz/tree/main/coverage_agents),
  [LCOV-клиент](https://github.com/TNO-S3/WuppieFuzz/blob/main/src/coverage_clients/lcov_client.rs).
  Доступный LCOV-путь учитывает покрытие строк; его нельзя автоматически
  приравнять к обратной связи по рёбрам C++. Сброс покрытия также не сбрасывает
  прикладное состояние сервиса.
- **DeepREST:** [статья авторов](https://arxiv.org/abs/2408.08594).
  Проверяем пользу обучения именно для наших коротких цепочек, без предположения,
  что оно обязательно даст преимущество.
- **Hypothesis:** [stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html).
  Выполнение Python-теста и доступ к исходникам сами по себе не дают обратную
  связь из C++-процесса. Готовая интеграция с async testsuite пока не проверена.

## На чём сравнивать

Стенд — [simple-target-service](services/simple-target-service/README.md),
контракт — [OpenAPI 3.0.3](services/simple-target-service/openapi.yaml).

| Сценарий | Что должен обнаружить инструмент |
| --- | --- |
| `/stateless/crash` | Вход, завершающий процесс |
| `/stateless/error` | HTTP 500 при живом процессе |
| `/stateful/sequence` | Последовательность вызовов одной ручки, завершающая процесс |
| `/shared/prepare` + `/shared/commit` | Цепочка с передачей ticket и повторным вызовом |
| `/dependency/crash` | Сбой при сочетании входа и ответа внешней зависимости |

Первые четыре сценария — основной набор. Для пятого сначала фиксируем ответ
зависимости одинаково для всех кандидатов. Генерацию ответов моков и изменение
окружения оцениваем отдельным экспериментом: обычный клиентский API-фаззер
не обязан управлять зависимостью.

## Порядок и правила экспериментов

1. Первая очередь: Schemathesis, RESTler и EvoMaster в black-box-режиме.
2. Затем WuppieFuzz без покрытия сервера, RestTestGen/DeepREST и контрольный
   Python-вариант на Hypothesis с явно описанной обвязкой.
3. Отдельный этап — WuppieFuzz с C++-покрытием. Это отдельная конфигурация
   эксперимента с учётом стоимости адаптера и инструментации.

Для каждого запуска фиксируем версию, конфигурацию, начальный корпус, seed,
число запросов, бюджет времени, найденные сценарии и время до первой находки.
Делаем несколько запусков. Учитываем стоимость перезапусков и сброса состояния;
внутри одной цепочки состояние сохраняем. Сохраняем и повторяем всю цепочку
со свежего окружения, оцениваем возможность её сокращения.

Падение подтверждаем завершением процесса, HTTP 500 учитываем отдельно.
Сетевой разрыв или таймаут сами по себе не доказывают crash. Известные
репродукторы из README стенда используем для проверки измерений, не добавляем
их скрытно в стартовый корпус. Ручные подсказки о зависимостях и последовательностях
документируем; прогоны со схемой и с дополнительными подсказками различаем.
